# ChatGPT Web Goal Mode (protocol monitoring and background browser sending)

Goal Mode is an opt-in monitor for an existing Rel.AI work session. It does not create another planning agent or use browser extensions. ChatGPT remains responsible for the task; Rel.AI observes factual work receipts and the conversation's current message branch.

## Installation and activation

Rel.AI ships `/goal` instructions inside the built-in `skills/rel-ai-workflow/SKILL.md`. No separate skill installation or new MCP tool is needed. Update/reconnect Rel.AI so ChatGPT can discover the revised skill and `relai_work` schema.

Use `/goal`, `/goal mode`, or an explicit request such as "run this in Goal Mode" to request Goal Mode. `/loop` and explicit Loop Mode requests select ongoing monitoring. Questions, negations, quoted examples and repository text never select a mode. The workflow instructions teach the model to pass the selected mode explicitly; they do not guarantee model selection without live evaluation.

Every `relai_work begin` now requires `mode: "normal" | "goal" | "loop"`. Internal callers and examples use `normal` for ordinary work, which makes zero ChatGPT discovery requests. Missing or contradictory modes fail before task creation. Legacy `goal:true` callers must add `mode:"goal"`; their default fixed strategy is preserved unless an explicit strategy is supplied. Existing enabled Goal/Loop records retain their mode, counters, bindings and unresolved sends.

Task creation returns `modeAcknowledgement` with requested/effective mode and readiness. Goal/Loop intent and the linking receipt are persisted together before success is acknowledged. Linking readiness is distinct from accepted intent. Enable monitoring on an existing task through `goal_update` with the exact `work_id` and requested mode. Bare commands preserve the established objective; they do not create unrelated work. Pause/Stop remain explicit lifecycle controls.

Connector activation returns an inline cryptographically random `chat_link` and a `pairingMarker` formatted as `Rel.AI Goal pairing: <work_id>:<link_id>`. ChatGPT writes that exact marker as one plain-text line in its first normal reply; no resource read, attachment, or file-materialization permission is requested. Rel.AI projects only marker IDs from completed assistant messages on the active conversation branch, then checks the task owner, tunnel and persisted marker before binding. The marker is correlation evidence, not execution authority. Existing private `relai://chat-link/{workId}/{linkId}` resources can still be read for older sessions; they are no longer advertised at task start. Inline tool receipts and completed legacy resource reads remain verifiable, but titles, timestamps, model-authored claims without an exact marker, and opaque host IDs never authorize linking.

Goal/Loop creation does not fetch account conversation metadata. For new marker-based sessions the monitor first checks the newest ordinary conversation and stops when the exact marker is verified; if unmatched it falls back to the shared bounded ordinary-and-Project catalogue. A trusted exact conversation ID, when genuinely available, bypasses catalogue reads but still requires exact active-branch proof. Titles and newest-chat position alone cannot bind a goal. No user URL input is required.

An explicitly proposed conversation hint remains pending during a bounded receipt-visibility window rather than being rejected on the first missing receipt while the originating turn is still saving. It is never eligible for continuation before receipt verification. If it remains unverified, Rel.AI drops the hint and resumes automatic discovery. Goal begin responses also include the same bounded work/link receipt as a standalone JSON text content part alongside the pairing marker: hosts that retain tool-result text but omit resource-read metadata can still supply verifiable evidence on the active branch.

Pending Goal/Loop status reissues the same pairing marker, allowing an existing unbound task to establish evidence in its originating chat on its next normal reply. It does not restart stopped goals, restore omitted historical receipts, or prove that a live host preserves the assistant marker. An older unbound chat outside the bounded discovery catalogue still needs fresh activity to become eligible, or an independently verified exact conversation association. Upgrades must verify that the actual ChatGPT host retains the new reference before claiming live linking or continuation success.

Only requested Goal/Loop tasks discover chats. The account catalogue merges ordinary-chat metadata and five recent previews per Project, completes sidebar pagination, deduplicates conversation IDs and ranks by update time. The shared catalogue retains up to 40 recent conversations across both sources; discovery inspects four new, changed, or expired conversation bodies per pass. A missing preview triggers a Project metadata listing; missing timestamps or incomplete pagination defer body reads. The integration depends on ChatGPT Web's undocumented recent-preview ordering and listing freshness; live acceptance must verify those assumptions and that ordinary assistant marker lines are preserved without file approval. An unmatched receipt advances to the next uninspected IDs; newly arriving chats and changed metadata are merged by conversation ID without restarting earlier work. Expired negative evidence can be revisited for late receipts. The finite 40-candidate catalogue is a bounded coverage limit, not a guarantee of full account discovery. A known exact conversation or verified owner/tunnel association bypasses global discovery but still requires the current work receipt.

One account-scoped coordinator shares candidate projections among pending goals. A SQLite lease serializes discovery across runtimes. The durable index holds bounded metadata and up to 40 bounded receipt projections, never full transcripts or credentials. Catalogues and candidate evidence expire after 60 seconds even if listing timestamps do not change. Sharing evidence across pending goals avoids repeating unchanged body reads within the freshness window, while allowing subsequent passes to advance in batches of four under the same account read budget. Newly issued task receipts invalidate older discovery evidence. Negative cache entries are temporary while receipts propagate. A cached match always receives a fresh active-branch verification before binding. Duplicate ordinary and Project catalogue entries preserve Project membership. Metadata pagination checkpoints survive restart and never authorize partial account rankings. A linked goal stays on its verified conversation even after that chat leaves the bounded discovery catalogue.

Discovery preserves the 5, 5, 10, 15, 20 second short retry schedule and then waits two minutes between attempts. Account budgets and upstream cooldown deadlines take precedence and do not consume continuation retries. Ordinary-task speculative detection records from older builds are retired on monitor startup; enabled goal records remain authoritative. Sign-in resumes only its own authentication waits. Discovery never asks for manual URL recovery.

## Acceptance of mode selection and discovery

Before claiming live reliability, test the updated plugin with `/goal`, `/goal mode`, `run this goal`, `run this in Goal Mode`, `run as goal`, `/loop` and explicit Loop Mode requests. Require the actual begin/activation arguments, matching acknowledgement, receipt binding, continuation acceptance and a subsequent tool call on the same work_id. Questions such as "what is Goal Mode?", negations and quoted commands must not activate monitoring. Natural-language routing remains model behavior; parser and fixture tests do not prove live selection.

Verify Project preview recency on a real authenticated account, including a newer chat in a Project on a later sidebar page. Then exercise app restart, stale listings, delayed receipts, cooldowns, multiple simultaneous goals, branch changes and Stop. A successful HTTP read or accepted mode alone is not end-to-end continuation proof. A live acceptance test must verify that linking and automatic continuation work when file materialization is ignored for more than 50 seconds. Live tests must preserve the existing account/tunnel boundary and never replay an uncertain send.

## Local authentication

In the Rel.AI desktop app, open **Settings → Connection → Goal Mode**, select the tunnel connection, and select **Sign in to ChatGPT**. Use the ChatGPT account that owns that tunnel. Finish login, MFA, or verification directly in the Browser page; Rel.AI checks sign-in automatically while the login page is open. The account card shows the signed-in account name or email. **Refresh sign-in** checks again on demand. **Sign out** clears only the selected connection's account and closes only its sign-in/continuation pages. A task's Sign in link selects its own tunnel. Verified sign-in resumes only that tunnel's authentication waits, including an exhausted authentication retry budget. Explicitly stopped goals and goals paused for other reasons remain unchanged; uncertain submission intent is preserved.

Every configured tunnel has a separate persistent browser profile under the app's user-data directory, derived from its Tunnel ID. Cookies, credentials and account sessions are never shared or automatically copied between tunnels. Labels may change without changing the profile. Changing or removing a Tunnel ID never silently reassigns its goals or transfers its sign-in. Account identity is visible only in the local account card; passwords and tokens never enter MCP outputs, task logs, or dashboard data.

Multiple tunnels share one local MCP server, but each tunnel-client forwards a different local bearer derived from the installation secret and its configured Tunnel ID. Core authenticates that credential as a distinct tunnel principal; a caller-supplied header or chat metadata cannot select another principal. Goals store the authenticated Tunnel ID and use its exact profile for discovery, reads, Stop, Send and receipt reconciliation. Disabled or removed connections lose scoped authentication. Local dashboard access keeps its existing installation credential. Existing workspace permissions remain installation-controlled.

Earlier global Goal Mode sign-in data and work records are preserved. They are not automatically assigned to a new tunnel identity. Sign in separately for each configured connection and start new scoped work sessions for goals created under the previous shared tunnel identity; do not silently adopt another account's work.

The local service reads ChatGPT conversation state through allowlisted protocol paths in the Electron main process, with authentication attached inside the dedicated browser session. When a Goal continuation is ready, Electron uses an on-demand hidden Chromium window with the same session to submit it through ChatGPT's normal composer. The older `REL_AI_CHATGPT_WEB_BEARER` and `REL_AI_CHATGPT_WEB_COOKIE` environment variables remain optional for non-desktop development; they are not needed for the desktop sign-in flow. Do not paste credentials into chats or commit them to the repository.

The integration uses ChatGPT Web's internal undocumented protocol for conversation reads and does not attempt to bypass interactive verification. Unsupported auth challenges, missing conversation permissions, model limits, or protocol changes can pause Goal Mode. This setup requires a separately established authenticated session; it does **not** take credentials automatically from your ordinary browser.

## Monitoring and control

Conversation discovery is shared by authenticated account and tunnel. Catalogue metadata is cached for 15 seconds; concurrent tasks share candidate evidence and in-flight reads. Exact receipt evidence and continuation preflight are read fresh before linking or sending. Previously verified host-session-to-conversation associations prefer their exact chat for later goals under the same account, without bypassing the new work receipt check. Tasks with active local operations or approval/blocker waits do not poll ChatGPT unless an uncertain submission needs reconciliation.

Each account has a maximum of 30 protocol reads per minute. HTTP 429 stops requests for the whole account, honors a bounded `Retry-After` (at least one minute), and otherwise backs off from five minutes exponentially. The cooldown is durable across service restarts and new task creation. Waiting for a shared cooldown or read budget does not consume a task's retry allowance. Repeated actual rate-limit responses remain bounded. Authentication is shared in flight and cached in the Electron process for at most one minute; sign-out, an explicit sign-in refresh, or HTTP 401 invalidates it. Credentials never enter IPC results or persisted cooldown records.

Requested goals retain a sanitized discovery reason and next attempt deadline in `relai_work goal_status`. One cancelled caller cannot cancel a shared discovery request; ownership and receipt checks remain mandatory.

The desktop service checks active goals every 30 seconds and ordinarily requires a stable, completed assistant message plus no active Rel.AI calls, approval wait, or blocked task before considering continuation. Stalled unfinished turns have a separate Stop-and-verify recovery path described below. It rereads the conversation just before sending. The exact prior node is recorded transactionally **before** opening the background sender. Immediately before its single Send activation, the sender checks that the ChatGPT conversation is still on that exact node and that its composer contains precisely the intended prompt. It considers the send accepted only when a protocol read finds that prompt on the new branch descending from the claimed node. Uncertain outcomes enter receipt verification without automatically resending. Task activity changes, approval waits, cancellation and completion invalidate an in-flight native handoff during navigation and composer preparation.

Desktop continuation sends through a temporary, normally hidden Electron BrowserWindow using the dedicated signed-in ChatGPT session. It does not inject challenge tokens or attempt to defeat Turnstile, proof-of-work, or `so`; those are handled, where possible, by the site's normal browser experience. The window stays alive during response generation and closes after an authenticated read confirms a completed assistant turn. Failed attempts never automatically reveal a browser. Confirmed pre-Send failures close their hidden window; possibly submitted messages retain a hidden page for receipt verification and response settlement, for at most one hour. Login remains an explicit Browser page action. It supports the current `#composer-submit-button` and form submit controls and checks ProseMirror text without zero-width placeholder characters. The dedicated Goal Mode sender replaces any restored text draft in its composer (rather than appending or refusing to continue). It first verifies the exact conversation branch, selects the editor's existing content, inserts the new continuation once, and verifies the full replacement before focusing Send and issuing a single native Enter key (no hidden-window coordinates). It does not change drafts in other conversations. When the prepared draft cannot be verified or the submit control cannot be located, the Goal Mode error distinguishes the two failures without disclosing the draft. It never resends a possibly accepted message on the same claimed branch. A browser receipt proving Send was never attempted allows the claim to be released for a bounded automatic retry. Authenticated protocol reads retain their 15-second network deadline even with a caller cancellation signal, and a failed browser handoff includes a sanitized stage such as `navigation`, `composer`, `draft`, `send_button` or `readback`. The legacy direct-protocol submission code remains available only to explicit non-desktop fixture/development transports: it requests chat-requirements preparation and finalization before preparing a conversation, passes the resulting token to conversation preparation, and uses one message ID across preparation and `POST /backend-api/f/conversation`, preserving the exact parent message ID. The obsolete null-`p` request is not used. Requirements preparation/finalization may require several distinct checks: `proof-of-work` (background computation), `Turnstile` or `Arkose` (browser verification), and `so` (opaque browser-signal check). If any is required, Goal Mode stops before submission and reports just the check names and phase. A proof-of-work requirement alone is **not** evidence of a visible CAPTCHA. Probes use `GET /backend-api/conversation/{id}` and `GET /backend-api/conversations`. Stream events are consumed without storing full text. A rejected request reports only the known stage (chat requirements, conversation preparation, or message submission) and HTTP status; no account tokens, remote error bodies, or conversation text enter task errors. If ChatGPT requires a Sentinel challenge Rel.AI cannot complete, the goal exhausts its bounded checks and pauses quietly without attempting to circumvent it. The Task inspector displays the sanitized reason, and `relai_work goal_status` returns `{ challenge: { phase, types } }`. Tokens, proof seeds/difficulty and encrypted challenge payloads never enter task logs. A missing finalization token is reported separately from a challenge. The user's normal ChatGPT webpage can handle required browser checks during a manually sent message; this does not automatically resume or prove that external protocol continuation supports the MCP connector.

Goal Mode streams ChatGPT conversation JSON and retains only bounded branch metadata, `/goal` command text, exact continuation receipts and work IDs extracted from bounded JSON receipts. Sender cleanup uses the same projection. The Electron browser projects the response before IPC; the service fallback uses the same parser. It never buffers or parses the full conversation body into an object. A 256 MiB wire-transfer safety budget and node/command bounds remain to reject unbounded or malformed responses, independent of memory retained. The unrelated small protocol responses keep their existing JSON safety limit. If an assistant turn stays unfinished for **4 minutes 30 seconds after the last Rel.AI tool call**, with no tool operation currently active, Goal Mode attempts recovery. Each new Rel.AI tool call resets that timer, even when the overall task has run for hours. It claims the exact unfinished branch before recovery, asks its signed-in browser to activate the matching ChatGPT Stop button, and confirms that the Stop control disappeared and the assistant response reached an explicitly ended or interrupted state before attempting a new continuation in the same conversation. Both the conversation branch and task activity are reread before sending. If ChatGPT cannot be stopped or the control is missing, recovery retries within the same bounded budget after rechecking the exact branch. A possibly submitted continuation is only reconciled by its receipt; recovery never reveals a browser. Automatic recovery does not cancel Rel.AI work processes and cannot control a different user's ordinary ChatGPT browser tab. ChatGPT Web connection interruptions themselves are outside Rel.AI's control.

When a Goal Mode work plan is explicitly updated through `relai_work plan` to contain only completed, skipped, and genuinely blocked steps (and at least one completed), Rel.AI uses its existing verified work-session finish path to close the task, retaining the blocked step descriptions. The monitor then reports the blocked or finished outcome instead of sending a redundant follow-up. An unfinished plan is never inferred complete from chat text. If safe finalization fails, Goal Mode reports `needs_finalization` instead of treating a browser handoff failure as the task outcome. The assistant should explicitly call `relai_work action:"complete"` before a final report once achievement is supported. The legacy `finish` operation can still finalize a supported Goal.

Each failed continuation gets **five automatic retries after its initial attempt**, with delays of **5, 5, 10, 15 and 20 seconds**. The retry count and deadline are durable across service restarts. Retry deadlines have their own wake-up timer, independent of the ordinary 30-second observation cadence. Confirmed unsent attempts retry the sender; uncertain outcomes use those retries only to inspect the exact prompt and claimed ancestor for an acceptance receipt. Native sender contention defers for five seconds without consuming that budget. After exhaustion, Goal Mode pauses and reports the reason in task status without opening a browser. An explicit new activation resets the retry budget but preserves uncertain intent, so a restart cannot duplicate a message. A successful receipt resets the failure budget. `goal_status` exposes `retryCount`, `maxRetries` and the next attempt time.

A goal also pauses if the previous continuation produces no new Rel.AI task activity, or after eight continuations. These bounds prevent endless self-replies. Explicit `relai_work finish`, task failure, or cancellation ends the goal.

## Explicit completion contract

Use `relai_work action:"complete"` with the exact `work_id` and a factual `summary` to finish a successful task in normal, Goal, or Loop mode. Completion reuses the existing task closure/validation-state recording path, persists a terminal `completed` status, marks the Goal/Loop record `finished` with `objectiveAchieved:true`, and disables subsequent automatic continuations. Repeated completion returns an idempotent receipt; terminal tasks cannot resume. Adaptive Goals require current objective-achievement evidence even if their monitor was stopped. Validation status is reported as observed (`passed`, `stale`, `failed`, `not_run`, or `not_required`); this operation does not fabricate passing checks or waive existing evidence requirements.

The legacy `finish` action closes ordinary tasks and supported Goals but completes **only an iteration** of an active Loop. `relai_validate` with `complete:true` likewise records a Loop iteration rather than ending that ongoing session. All plan steps marked completed are not by themselves proof of objective achievement or a terminal transition. `goal_stop` disables monitoring without claiming success, `cancel` aborts the task, and failed tasks retain their failure state. A chat-linking or HTTP 429 cooldown cannot override a persisted successful completion. The Tasks inspector and `goal_status` read that durable state.

An explicitly ended, interrupted, or cancelled assistant reply is settled for continuation; this is separate from the work session being complete. A previously interrupted reply does not require pressing Stop again. Recovery requires a fresh settled-branch read even after the browser reports a successful Stop. The task's status, active calls, call count and last activity are checked again before continuation. Failed and cancelled work sessions retain those outcomes; an unavailable work session stops monitoring with completion unknown. The next ordinary monitor cycle observes task closure, normally within 30 seconds while the service is running.

In the Rel.AI desktop Tasks inspector, select a Goal Mode task and use **Stop Goal** to disable further automatic sends without cancelling the work session or its processes. The button is shown only for active goals. ChatGPT can also call `relai_work` with `action:"goal_status"` to inspect the exact work ID, or `action:"goal_stop"` to disable monitoring. A network request already accepted by ChatGPT may complete after the user stops the goal; it cannot be withdrawn retroactively. Stopping the task itself remains the separate `relai_work cancel` operation.

## Limitations

- The desktop Tasks inspector has a **Stop Goal** button. It controls the same persisted goal record as `relai_work goal_stop`; there is no separate MCP tool.
- Changes to ChatGPT's private endpoints, SSE framing, session refresh, and challenge flow are outside Rel.AI's compatibility contract.
- Live authenticated conversation reads **passed** on 2026-10-12. The original write attempt failed with HTTP 422; after updating the installed build, repeat tests on two accounts reached a Sentinel requirements challenge before message submission. No messages were sent and MCP re-entry remains unproven. The earlier builds did not capture which check was required; this revision records only the specific check names and phase.
- Desktop Goal Mode requires a signed-in, locally authenticated ChatGPT session and a uniquely linked conversation. Check sign-in does not establish protocol compatibility; HTTP requests can still fail as endpoints change.
- The authenticated protocol bridge, background composer sender, stale-branch checks, verification handoff and session isolation have automated fixture coverage. Live same-thread browser submission and MCP re-entry still require a freshly installed desktop build and an authenticated end-to-end test before production readiness can be asserted.

## Audit on 2026-10-13

The checkout supports unattended ordinary continuation, but full autonomy is not established for the installed application. Audit evidence comes from the current source, isolated work-session tests, a real hidden Electron composer fixture, and read-only inspection of installed files and stored Goal Mode records. No live goal was restarted or continuation submitted during this audit.

| Requirement | Observed behavior and boundary |
| --- | --- |
| Continue with the same work ID and objective | The continuation includes both, asks for current receipts first, and uses the exact claimed conversation branch. An uncertain submission pauses without replaying it. |
| Stop a stalled response before sending | The assistant branch must have no active Rel.AI operation and 4:30 of tool inactivity. The hidden browser activates Stop once, verifies settlement, then the monitor rereads branch and task state before Send. |
| No routine browser click | Real Electron fixture input activates Send and Stop while the window remains hidden. Login, interactive verification, an unavailable control or an uncertain result still needs attention. Actual ChatGPT acceptance and subsequent MCP activity remain a separate end-to-end check. |
| Stop when the work is done | An explicit finish ends monitoring on the next cycle. An explicitly resolved `relai_work plan` uses guarded task completion. A resolved plan received through another progress path can instead stop the goal as `needs_finalization`; it is not proof that cleanup and task closure succeeded. A final chat message alone does not close the task. |
| Avoid endless recovery | Both settled-turn continuation and stalled-turn recovery stop after eight continuations or after a prior continuation fails to produce new Rel.AI task activity. |
| Installed application parity | Installed service and Electron files differ from this checkout. Stored attempts include browser handoff failures and one record with an accepted continuation count of one; that count alone does not demonstrate MCP re-entry or completed work. |

The audit corrected interrupted replies being treated as still running, missing task rechecks after the final conversation read, acceptance of an unfinished recovery readback, inconsistent no-activity limits between recovery paths, and failed/cancelled/missing tasks being described as finished. The browser now recognizes an already interrupted reply without another Stop activation and closes its retained page when the reply settles. Stop recovery receives the same bounded native-request budget as browser continuation because navigation and authenticated readback can exceed the budget for a single protocol read. The existing Goal Mode test executables are registered in the everyday runner; its previous unclassified-test error prevented the parent suite from starting.

Remaining integration gaps are explicit: recovery currently handles an unfinished **assistant** node, so a conversation left on a user or tool node does not enter that path. Rel.AI cannot establish that a new browser window can stop generation owned by an ordinary browser tab until that exact cross-window flow is tested. Automatic `/goal` discovery searches only 20 recent conversations and requires the command near work creation; explicit linking avoids that lookup. The desktop service must remain running and its dedicated ChatGPT session authenticated. Browser automation cannot guarantee unattended recovery from account limits, protocol drift or interactive verification.

Production acceptance still requires the updated installed build to demonstrate: an existing ChatGPT task stalls, Rel.AI stops that exact response without a user click, one continuation is accepted in the same conversation, ChatGPT calls Rel.AI again with the same work ID, and explicit task completion prevents further continuations. Source and fixture validation do not replace that acceptance sequence.

Validation on Windows passed: all 23 Goal Mode unit cases, the MCP Goal Mode lifecycle smoke, browser surface and native service bridge regressions, `npm run test:electron` including the real hidden Chromium input fixture, `npm run check`, and all 159 everyday executables under `node test/run-tests.mjs`. The first everyday run reached 157/159: its remaining failures were an outdated work-action schema expectation and the dashboard source fingerprint after adding the conversation-parser dependency. The schema test now validates both Goal controls and their required work ID. `npm run build:frontend` regenerated the fingerprint with identical dashboard asset hashes, and the exact parent runner then passed. No release packaging, installation, live ChatGPT continuation or push was performed.
