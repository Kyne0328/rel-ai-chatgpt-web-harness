# ChatGPT Web Goal Mode (protocol monitoring and background browser sending)

Goal Mode is an opt-in monitor for an existing Rel.AI work session. It does not create another planning agent or use browser extensions. ChatGPT remains responsible for the task; Rel.AI observes factual work receipts and the conversation's current message branch.

## Installation and activation

Rel.AI ships `/goal` instructions inside the built-in `skills/rel-ai-workflow/SKILL.md`. No separate skill installation or new MCP tool is needed. Update/reconnect Rel.AI so ChatGPT can discover the revised skill and `relai_work` schema.

Use `/goal` (for an established task) or `/goal <objective>` in a normal ChatGPT conversation. A normal `relai_work begin` from ChatGPT Web now triggers a bounded, asynchronous read-only check of recent ChatGPT conversations, even if ChatGPT omits `goal:true`. Rel.AI activates Goal Mode only when exactly one recent conversation's **latest user message** starts with `/goal` (excluding `/goal stop`, `/goal cancel`, and `/goal status`). The command is claimed once, so unrelated tasks cannot reuse it. A rewritten task objective does not have to match the original prompt verbatim.

For bare `/goal`, ChatGPT must infer the objective from established work. Explicit `goal:true` and the optional `conversationUrl` remain supported. Without a URL, Rel.AI reads at most 20 recent conversations and never guesses among multiple matches. The initial lookup does not block task creation; if the command is not yet visible, one more bounded lookup runs on the monitor's next cycle. Use `relai_work goal_status` to inspect `checking`, `ambiguous`, `not_requested`, `needs_auth` and active states. Ordinary non-ChatGPT task calls are not scanned.

## Local authentication

In the Rel.AI desktop app, open **Browser → ChatGPT · Goal Mode → Sign in to ChatGPT**. Finish login, MFA, or verification directly in the embedded Chromium page, then select **Check sign-in**. Use **Sign out** to clear this Goal Mode account's dedicated saved browser data. Goal Mode uses a persistent profile under the app's user-data directory that is separate from normal browser automation sessions. Sign-in credentials are not exposed to MCP tool outputs, task logs, or the dashboard.

The local service reads ChatGPT conversation state through allowlisted protocol paths in the Electron main process, with authentication attached inside the dedicated browser session. When a Goal continuation is ready, Electron uses an on-demand hidden Chromium window with the same session to submit it through ChatGPT's normal composer. The older `REL_AI_CHATGPT_WEB_BEARER` and `REL_AI_CHATGPT_WEB_COOKIE` environment variables remain optional for non-desktop development; they are not needed for the desktop sign-in flow. Do not paste credentials into chats or commit them to the repository.

The integration uses ChatGPT Web's internal undocumented protocol for conversation reads and does not attempt to bypass interactive verification. Unsupported auth challenges, missing conversation permissions, model limits, or protocol changes can pause Goal Mode. This setup requires a separately established authenticated session; it does **not** take credentials automatically from your ordinary browser.

## Monitoring and control

The desktop service checks active goals every 30 seconds and ordinarily requires a stable, completed assistant message plus no active Rel.AI calls, approval wait, or blocked task before considering continuation. Stalled unfinished turns have a separate Stop-and-verify recovery path described below. It rereads the conversation just before sending. The exact prior node is recorded transactionally **before** opening the background sender. Immediately before its single Send activation, the sender checks that the ChatGPT conversation is still on that exact node and that its composer contains precisely the intended prompt. It considers the send accepted only when a protocol read finds that prompt on the new branch descending from the claimed node. Uncertain outcomes pause without automatically resending.

Desktop continuation sends through a temporary, normally hidden Electron BrowserWindow using the dedicated signed-in ChatGPT session. It does not inject challenge tokens or attempt to defeat Turnstile, proof-of-work, or `so`; those are handled, where possible, by the site's normal browser experience. The window stays alive during response generation and closes after an authenticated read confirms a completed assistant turn. If login, verification, an unknown composer state, or an uncertain send needs attention, the window becomes visible and Goal Mode pauses. It supports the current `#composer-submit-button` and form submit controls and checks ProseMirror text without zero-width placeholder characters. The dedicated Goal Mode sender replaces any restored text draft in its composer (rather than appending or refusing to continue). It first verifies the exact conversation branch, selects the editor's existing content, inserts the new continuation once, and verifies the full replacement before focusing Send and issuing a single native Enter key (no hidden-window coordinates). It does not change drafts in other conversations. When the prepared draft cannot be verified or the submit control cannot be located, the Goal Mode error distinguishes the two failures without disclosing the draft. It never sends automatically a second time on the same claimed branch. Authenticated protocol reads retain their 15-second network deadline even with a caller cancellation signal, and a failed browser handoff includes a sanitized stage such as `navigation`, `composer`, `draft`, `send_button` or `readback`. The legacy direct-protocol submission code remains available only to explicit non-desktop fixture/development transports: it requests chat-requirements preparation and finalization before preparing a conversation, passes the resulting token to conversation preparation, and uses one message ID across preparation and `POST /backend-api/f/conversation`, preserving the exact parent message ID. The obsolete null-`p` request is not used. Requirements preparation/finalization may require several distinct checks: `proof-of-work` (background computation), `Turnstile` or `Arkose` (browser verification), and `so` (opaque browser-signal check). If any is required, Goal Mode stops before submission and reports just the check names and phase. A proof-of-work requirement alone is **not** evidence of a visible CAPTCHA. Probes use `GET /backend-api/conversation/{id}` and `GET /backend-api/conversations`. Stream events are consumed without storing full text. A rejected request reports only the known stage (chat requirements, conversation preparation, or message submission) and HTTP status; no account tokens, remote error bodies, or conversation text enter task errors. If ChatGPT requires a Sentinel challenge Rel.AI cannot complete, the goal pauses rather than trying to circumvent it. The Task inspector displays the sanitized reason, and `relai_work goal_status` returns `{ challenge: { phase, types } }`. Tokens, proof seeds/difficulty and encrypted challenge payloads never enter task logs. A missing finalization token is reported separately from a challenge. The user's normal ChatGPT webpage can handle required browser checks during a manually sent message; this does not automatically resume or prove that external protocol continuation supports the MCP connector.

Authenticated conversation reads are bounded at 32 MiB rather than 8 MiB to accommodate long development threads without unlimited buffering. If an assistant turn stays unfinished for **4 minutes 30 seconds after the last Rel.AI tool call**, with no tool operation currently active, Goal Mode attempts recovery. Each new Rel.AI tool call resets that timer, even when the overall task has run for hours. It claims the exact unfinished branch once, asks its signed-in browser to activate the matching ChatGPT Stop button, and confirms that the Stop control disappeared and the assistant response reached an explicitly ended or interrupted state before attempting a new continuation in the same conversation. Both the conversation branch and task activity are reread before sending. If ChatGPT cannot be stopped, the control is missing or the result is uncertain, it pauses and reveals the browser rather than risk duplicate work. Automatic recovery does not cancel Rel.AI work processes and cannot control a different user's ordinary ChatGPT browser tab. ChatGPT Web connection interruptions themselves are outside Rel.AI's control.

A goal also pauses if the previous continuation produces no new Rel.AI task activity, or after eight continuations. These bounds prevent endless self-replies. Explicit `relai_work finish`, task failure, or cancellation ends the goal.

In the Rel.AI desktop Tasks inspector, select a Goal Mode task and use **Stop Goal** to disable further automatic sends without cancelling the work session or its processes. The button is shown only for active goals. ChatGPT can also call `relai_work` with `action:"goal_status"` to inspect the exact work ID, or `action:"goal_stop"` to disable monitoring. A network request already accepted by ChatGPT may complete after the user stops the goal; it cannot be withdrawn retroactively. Stopping the task itself remains the separate `relai_work cancel` operation.

## Limitations

- The desktop Tasks inspector has a **Stop Goal** button. It controls the same persisted goal record as `relai_work goal_stop`; there is no separate MCP tool.
- Changes to ChatGPT's private endpoints, SSE framing, session refresh, and challenge flow are outside Rel.AI's compatibility contract.
- Live authenticated conversation reads **passed** on 2026-10-12. The original write attempt failed with HTTP 422; after updating the installed build, repeat tests on two accounts reached a Sentinel requirements challenge before message submission. No messages were sent and MCP re-entry remains unproven. The earlier builds did not capture which check was required; this revision records only the specific check names and phase.
- Desktop Goal Mode requires a signed-in, locally authenticated ChatGPT session and a uniquely linked conversation. Check sign-in does not establish protocol compatibility; HTTP requests can still fail as endpoints change.
- The authenticated protocol bridge, background composer sender, stale-branch checks, verification handoff and session isolation have automated fixture coverage. Live same-thread browser submission and MCP re-entry still require a freshly installed desktop build and an authenticated end-to-end test before production readiness can be asserted.
